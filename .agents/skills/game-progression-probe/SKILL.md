# Game Progression Probe

Use the full contract in [game progression testing](../../../docs/game-progression-testing.md).

## Procedure

1. Use the Morrowind MCP Player at autonomy level 4 in progression exploration mode. Start through `tests/start_server_mo2.ps1 -WaitForServer`. Do not issue MCP operations until this command reports that the configured TCP endpoint is responding; treat its timeout as a launch failure, not an attempted game operation.
2. Immediately after the endpoint responds, run `tests/mcp_discover.ps1 -OutputPath <run-directory>/initial-discovery.json` before any MCP tool operation. It creates an independent session, sends `initialize` and `notifications/initialized`, then records `tools/list` and `resources/list` (the generic record can also contain prompts, which the Player agent cannot execute and must ignore). Read the tools/resources evidence before choosing an operation. When Memory is listed, read `morrowind://memory/index.json` first and use its `links` as the canonical hierarchy for `resources/read`. Read the linked player, journal, quest, actor, dialogue, notification, or objective documents needed to understand the current instruction before selecting an action. When `resources/subscribe` is available, subscribe to the root index and only the goal-relevant upper-level indexes or collections. Subscribe to a dialogue, individual quest, or another leaf only while its actor or objective is the current focus. On `notifications/resources/updated`, re-read the notified URI; when the root index changes, re-evaluate its links and replace subscriptions with only the required upper-level indexes and temporary leaves. When an objective is completed, dialogue ends, target changes, or the player changes cells, unsubscribe leaves that are no longer relevant when `resources/unsubscribe` is available. If subscription, unsubscription, or notification monitoring is unavailable, re-read the root index and relevant descendants after each meaningful state change. Re-read the root index and related descendants after NPC speech, notifications, quest updates, or an ambiguous action result, and derive the speaker, instruction, objective, and next candidate action from the text rather than UI names, targets, or positions alone. Do not rely on selectors, waits, or capabilities from older runs. Before a state-changing operation that can change the capability surface, start `tests/mcp_discover.ps1 -WatchSeconds <action-specific timeout> -OutputPath <run-directory>/capability-watch.json` in a separate terminal. After the operation, read the watcher record: it refreshes the corresponding tools/resources list after a matching notification. If no watcher was active, run a new non-watching discovery snapshot after the state change and record that notification evidence was unavailable. Treat the latest discovery record and read-only state/UI tools as evidence; do not invoke an unconfirmed state-dependent capability. If discovery fails, record it as unavailable evidence and do not repeatedly invoke the same unconfirmed capability.
3. Find and invoke NEW GAME from the observed menu. Do not load a save before NEW GAME is complete.
4. Capture a screenshot after meaningful state changes and before risky or ambiguous actions. Prefer `mw-screenshot-save capture_with_ui=true` when UI state matters; avoid redundant captures during unchanged polling.
5. Iterate: observe state, write an assessment of the situation, evidence, remaining candidate actions, and decision, make one justified tool operation, wait only using an observed readiness condition, then observe state again. Choose that condition from the operation's expected effect, such as a menu change, player-control change, target/world change, or dialogue completion; do not use a generic menu-appearance condition. During animation, loading, or NPC speech, an unchanged observation is intermediate evidence until the action-specific wait expires. Consider `stalled` only after repeated observations show no expected milestone, no newly available capability, and no reasonable recorded candidate action.
6. Save every successful step in a schema version 1 JSON file under `tests/logs/game_progression/`. Include `intent`, operation, assertions, waits, observed summary, assessment, screenshot resource URIs, and notes so another agent can adapt to a changed UI.
7. Immediately before reporting `stalled` or `failed`, capture an evidence screenshot. The replay runner records up to two related read-only probes automatically: menu action uses menu/player state, player action uses player/target state, and player navigation uses player/world state. Record any additional observed probe responses, the final assessment, and all remaining or rejected candidates. If the latest discovery record exposes `mw-debug-action`, call it once with `action=memory:SaveDebugDocuments` before stopping the server, then record its success, unavailability, or error and the resolved dump directory `<Paths.modDataDir>\memory-dump`. A debug-dump failure is diagnostic evidence and must not replace the progression outcome. Then stop the server.
8. Validate the generated file with `tests/game_progression/run.py --validate-only`.
9. Report `completed`, `stalled`, or `failed`. For stalled, report the final assessment, screenshot URI, unchanged observations, attempted operations, remaining capabilities, and the policy values that led to the result. Stop the server for terminal failure and stalled outcomes.

## Replay

Use `tests/game_progression/run.py --scenario <scenario.json>` for deterministic replay. The runner executes the recorded operations and assertions; it does not rediscover the bootstrap path. If agent exploration succeeds but replay fails, improve the scenario contract or runner rather than weakening the observed test condition.
